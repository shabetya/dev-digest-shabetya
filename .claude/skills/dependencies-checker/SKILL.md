# dependencies-checker

Аудит залежностей репозиторію з єдиним звітом у фіксованому форматі. Скіл
**read-only**: нічого не встановлює, не оновлює й не редагує — лише читає файли
і (опційно) питає npm-реєстр про `outdated`/`audit`. Зміни залежностей — окремий
крок, який користувач вирішує сам після звіту.

Контекст репо: п'ять незалежних пакетів без workspace (кожен зі своїм
`package.json`/lockfile), крос-пакетні зв'язки йдуть через `tsconfig` path
aliases, а `@devdigest/shared` **вендориться копіями** в `server/` і `client/`
(див. `CLAUDE.md`). Тому звичайний `pnpm ls` на корені не дає цілісної картини —
саме цю прогалину закриває скіл.

## Крок 1 — зібрати дані (детерміновано, одним запуском)

```bash
python3 .claude/skills/dependencies-checker/scripts/collect.py --online
```

Прапорці: `--online` (додає `outdated` + `audit`, ходить у мережу; пропусти, якщо
користувач попросив офлайн), `--packages server,client` (звузити область).
Запускати з кореня репо. Скрипт — лише stdlib Python, друкує один JSON у stdout.

Чому скрипт, а не ручні `du`/`grep`: розмір транзитивного замикання, дедуп
hardlink-ів pnpm та парсинг alias-ів легко порахувати неправильно вручну, а
результат має бути відтворюваним між запусками. Твоя робота — **інтерпретація**.

Ключі JSON: `packages.<name>` (`deps[]` з `own_kb` / `with_transitive_kb` /
`transitive_count`, `prod_total_kb`, `all_total_kb`, `aliases[]`, `likely_unused[]`,
`online.outdated|audit`), `version_conflicts[]`, `shared_deps[]`,
`vendored_shared_drift`, `client_bundle`, `mermaid`, `warnings[]`.

Якщо `warnings` каже, що `node_modules` відсутній — не вигадуй розміри: познач
пакет як "не виміряно" і порадь встановити залежності. Якщо `--online` не
відпрацював (`online.* == null`) — так і напиши в розділі, не підміняй
припущеннями.

## Крок 2 — верифікувати кандидатів перед тим, як радити

Евристики скрипта дають кандидатів, не вердикти. Перед включенням у звіт:

- **`likely_unused`** — скрипт шукає імпорти в коді та згадки в scripts/конфігах.
  Хибнопозитивні: плагіни, що підвантажуються за іменем (`@fastify/autoload`,
  `pino-pretty`), бінарі в CI/docker, peer-залежності. Для кожного кандидата
  зроби `grep -rn "<name>" <pkg> --include=*.{ts,tsx,json,mjs,yml,sh} -l` (без
  `node_modules`) і прочитай згадку в коді. Підтверджене → "ймовірно зайве",
  неоднозначне → "перевірити вручну". Ніколи не пиши "видали" без перевірки:
  це реальна поломка збірки, якщо помилитися.
- **`version_conflicts`** — розбіжність діапазонів між пакетами. Зроби висновок
  лише про те, чи це критично (мажор різний) чи косметика (мінор).
- **`vendored_shared_drift`** — список файлів, що розійшлися. Для кожного
  розбіжного файлу зроби `diff server/src/vendor/shared/<f> client/src/vendor/shared/<f>`
  і одним реченням опиши суть (додане поле, інший enum…). CLAUDE.md прямо
  каже, що копії дрейфують — нове тут лише *що саме* розійшлося.
- **`client_bundle`** — якщо `available: false`, не рахуй бандл; якщо збірка
  стара (`built_at` давніше за останні зміни `client/package.json`), познач це.
  Атрибуції chunk→пакет скрипт не робить: для найважчих пакетів клієнта
  (`mermaid`, `recharts`, `lucide-react`, `react-markdown`) перевір `grep -rn`
  чи вони імпортуються через `next/dynamic`/динамічний `import()` — це головний
  важіль зменшення first-load.

## Крок 3 — вивести звіт у ТАКОМУ форматі

Українською, без зайвої прози. Порядок і заголовки незмінні — розробники мають
знаходити потрібну секцію за звичкою. Порожню секцію не пропускай, а пиши
"немає знахідок". Розміри — у MB (1 знак), з "KB" лише для <1 MB.

```markdown
# Dependencies report — DevDigest
_Дата: YYYY-MM-DD · Режим: online|offline · Пакети: server, client, …_

## 1. Резюме
3–5 пунктів: загальний розмір по пакетах, скільки знахідок P0/P1/P2,
головний висновок одним реченням.

## 2. Схема залежностей
(вставити `mermaid` зі скрипта у ```mermaid-блок; за потреби
спростити/підписати. Суцільна стрілка — path alias між пакетами,
пунктир — vendored-копія, блакитні вузли — топ-5 найважчих prod-залежностей.)

## 3. Розміри
### 3.1 По пакетах
| Пакет | Менеджер | Prod (MB) | Prod+dev (MB) | Dep-ів (prod/dev) |
### 3.2 Топ-10 найважчих залежностей (по всьому репо)
| # | Пакет | Де використовується | Власний (MB) | З транзитивними (MB) | Транзитивних |
### 3.3 Client bundle
total raw/gzip, кількість chunks, топ-5 chunks. Або "не зібрано: …".

## 4. Знахідки
### 4.1 Ймовірно невикористані    | Пакет | Залежність | Секція | Докази |
### 4.2 Дублікати / розбіжності версій   | Залежність | Пакети й діапазони | Критичність |
### 4.3 Outdated   | Пакет | Залежність | Поточна → Остання | Тип (major/minor/patch) |
### 4.4 Вразливості   | Пакет | Залежність | Severity | Суть |
### 4.5 Дрейф vendored shared   | Файл | Що розійшлося |

## 5. Пріоритизація
| Пріоритет | Дія | Пакет | Ефект | Зусилля (S/M/L) | Ризик |
Правила пріоритетів нижче. Відсортовано P0 → P3.

## 6. Поради
5–8 конкретних порад розробнику, кожна: що зробити + команда/файл + чому.
Закінчи блоком «Чого цей звіт не перевіряв» (ліцензії, транзитивні
вразливості без audit, runtime-використання).
```

### Правила пріоритетів (щоб оцінка була однаковою між запусками)

- **P0** — vulnerability severity high/critical у prod-залежності; мажорний
  дрейф `vendored shared`, що ламає контракт між server і client.
- **P1** — вразливість moderate; prod-залежність >20 MB з транзитивними, яку
  можна замінити/завантажувати динамічно; мажорна розбіжність версії однієї
  залежності між пакетами; підтверджено невикористана prod-залежність.
- **P2** — outdated minor/patch; невикористана dev-залежність; косметичний
  дрейф vendored; мінорна розбіжність діапазонів.
- **P3** — естетика й гігієна (прибрати `^` розбіжності, вирівняти менеджер).

Ефект оцінюй числом, де можливо ("−118 MB у node_modules", "−X KB у first-load"),
зусилля — S (<30 хв, одна правка), M (є зміни коду), L (міграція).

## Межі

- Не запускай `install`, `update`, `dedupe`, `remove`, `audit fix`, `docker`,
  `next build` — навіть якщо звіт радить їх; лише формулюй як пораду з командою.
- Не правь `package.json`, lockfile-и, `vendor/`, `dist/`, `clones/`.
- Не вигадуй цифр: усе в звіті має йти з JSON скрипта або з виконаної тобою
  перевірки; якщо не виміряно — так і пиши.
